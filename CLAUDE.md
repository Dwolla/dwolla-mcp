# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An MCP (Model Context Protocol) server for the Dwolla payment API, published as `@dwolla/mcp-server`. It exposes read-only Dwolla operations (accounts, customers, transfers, mass payments, funding sources, compliance/documents, webhooks, exchanges) as MCP tools that AI agents can call.

**Nearly all of `src/` is generated code.** This repo is a Speakeasy (https://speakeasy.com) MCP-TypeScript target. The SDK, tool definitions, models, and CLI are generated from Dwolla's OpenAPI spec via `.speakeasy/workflow.yaml` and regenerated on a daily cron / on-demand by `.github/workflows/sdk_generation.yaml` (using `speakeasy-api/sdk-generation-action`). Every generated file starts with:

```
/*
 * Code generated by Speakeasy (https://speakeasy.com). DO NOT EDIT.
 */
```

**Do not hand-edit files carrying that header** — they will be silently overwritten on the next generation run. If a change needs to persist, it belongs in one of the few non-generated extension points (see Architecture below) or in `.speakeasy/mcp-overlay.yaml` (an OpenAPI overlay applied before generation — e.g. to rename/prune operations exposed as MCP tools).

## Commands

```bash
npm run build       # bun i && bun src/mcp-server/build.mts && tsc — builds bin/mcp-server.js
npm run mcpb:build   # same, but also packs a Claude Desktop .mcpb bundle
npm run lint         # eslint --cache --max-warnings=0 src
npm run check        # alias for lint
```

There is no test suite in this repo (`gen.yaml` has `tests.generateTests: true` but no generated tests are currently checked in).

Run the built server locally against Dwolla sandbox:

```bash
node bin/mcp-server.js start --bearer-auth "your_token_here" --server sandbox
```

Full flag reference: `node bin/mcp-server.js --help` or `node bin/mcp-server.js start --help`.

## Architecture

**Generated layers** (do not edit directly — treat as read-only API surface):
- `src/funcs/` — one standalone SDK function per Dwolla API operation (e.g. `accountsGet.ts`), operating on a `DwollaMcpCore` client.
- `src/mcp-server/tools/` — one MCP tool wrapper per operation (e.g. `tool$accountsGet`), calling the matching function in `src/funcs/` and mapping the result via `formatResult`/`$inspect()` into MCP tool-call output.
- `src/mcp-server/server.ts` — `createMCPServer()` wires every `tool$*` into an `@modelcontextprotocol/sdk` `McpServer` instance, applies scope/annotation filters, and (when `--mode dynamic`) registers the meta-tools (`list_tools`, `describe_tool_input`, `execute_tool`, `list_scopes`) instead of the full tool set.
- `src/mcp-server/cli/{start,serve}/` — Stricli CLI command defs + impls. `start` runs stdio or SSE transport; `serve` runs Streamable HTTP transport (with `--disable-static-auth` to allow per-request credentials instead of a static bearer token).
- `src/models/` — Zod schemas + TS types for every request/response shape, keyed by operation.
- `src/lib/` — generated SDK plumbing: HTTP client, retries, security/auth, config, URL/encoding helpers.
- `src/core.ts` — `DwollaMcpCore extends ClientSDK`, the underlying HTTP client used by every function in `src/funcs/`.

**Extension points** (the intended place for custom logic, if ever needed — check whether a file still carries the "DO NOT EDIT" header before assuming it's safe to edit):
- `src/hooks/hooks.ts` / `src/hooks/registration.ts` — `SDKHooks` supports `sdkInit`, `beforeCreateRequest`, `beforeRequest`, `afterSuccess`, `afterError` hooks, registered via `initHooks()` in `registration.ts`. This is the sanctioned way to inject custom request/response behavior without touching generated files.
- `.speakeasy/mcp-overlay.yaml` — OpenAPI overlay applied to Dwolla's spec before generation; use this to change which operations become tools, rename them, or adjust descriptions/scopes.
- `.speakeasy/gen.yaml` — generator config (naming/versioning strategy, auth handling, response envelope format, etc.).

**Tool naming**: MCP tool names are kebab-case (`accounts-get`, `customers-transfers-list`, ...); the full list is documented in `README.md` under "Available Operations" and centralized in `src/tool-names.ts`.

**Scopes**: currently only one scope, `read` (`src/mcp-server/scopes.ts`) — this server is read-only by design; it cannot create customers, initiate transfers, or mutate account data.

**Auth/environments**: bearer-token auth against either `https://api-sandbox.dwolla.com` (`--server sandbox`) or `https://api.dwolla.com` (`--server prod`), selected via CLI flag/env, resolved in `src/lib/config.ts` (`ServerList`).

## Regenerating the SDK

Source of truth is Dwolla's OpenAPI spec at `Dwolla/dwolla-openapi` on GitHub (`main` branch), fetched by `.speakeasy/workflow.yaml`. Regeneration happens via CI (`sdk_generation.yaml`, daily cron + manual `workflow_dispatch` with `force`/`set_version` inputs), which opens a PR with the diff. Do not attempt to hand-write changes that regeneration would overwrite — change the overlay or upstream OpenAPI spec instead.
